# ADR-002: No NewsCore module for now

**Status:** Rejected for now (7 November 2026, #577). Revisit only under the condition at the end.
**Date:** 7 November 2026
**Deciders:** Mars Pater
**Reference:** branch `mars/newscore-spike-reference` (commit 50b53cc) keeps the attempted change. It does not compile and is not for merge.

## Context

`News.xcodeproj` has four native targets over the synchronized `Sources/` and `Tests/` folders. `News`, `NewsTestRunner`, `NewsHarness` and `NewsTests` each compile `Sources/` themselves, so CI compiles the same code up to four times (see [the harness build-path audit](../audits/2026-11-07-harness-build-path.md)). The 7 November engineering review approved a bounded, reversible spike: move one vertical slice into a static library `NewsCore`, link it into all four targets, and keep it only if measured builds improve, resources behave the same and the change fits one PR.

## Hypothesis

A static `NewsCore` library holding a self-contained slice compiles once and is linked four times. That shortens cold app builds, incremental builds after a core edit, and the native test-bundle build, without changing `Bundle.main`. A static library leaves `Bundle.main` as the app bundle, so `bundledModelResource` keeps working.

## Before-state

Apple M5, 10 cores, Xcode 27.0 (27A266a), main `cd68be0`, Sentry off, the worktree's own `build/DerivedData`. Three runs per case, run one at a time with the other session's builds held. The 1-minute load average was recorded at the start of each run.

| Case | Run 1 | Run 2 | Run 3 | Median | Load |
|---|---|---|---|---|---|
| Cold `./build.sh` (Release, `rm -rf build/DerivedData`) | 91 s | 95 s | 99 s | **95 s** | 2.6 / 8.1 / 10.3 |
| Incremental `./build.sh` after touching `Sources/Models/FeedError.swift` | 6 s | 5 s | 5 s | **5 s** | 9.5 / 11.6 / 10.1 |
| Incremental `./build.sh` after touching `Sources/Views/List/ArticleCardView.swift` | 5 s | 5 s | 5 s | **5 s** | 8.6 / 11.1 / 9.6 |
| `xcodebuild build-for-testing -scheme News -only-testing:NewsTests`, cold DerivedData (Debug) | 62 s | 68 s | 72 s | **68 s** | 9.0 / 12.0 / 14.3 |

The incremental loop is already near the floor of what can be measured. Only the cold app build and the test-bundle build had room to improve.

## The slice as attempted

About 10,000 lines, roughly 17% of `Sources/`:

- **Whole files moved with `git mv`:**
  - `Sources/Models` (16 files);
  - `Services/DateParser`, `NetworkTimeline`, `IPAddressValidator`, `NetworkBoundaryProxy` and `SecureHTTPClient`;
  - `Intelligence/Extraction/ContentExtractionPipeline`.
- **Types split out of files that stayed in the app:**
  - `NewsCategory`, `EntityType` and `EntityResult` from `ArticleIntelligence.swift`;
  - the `StoryImportance` enum from `StoryImportance.swift`;
  - `ArticleContentRedactor` from `ArticleIntelligence.swift`, which the compiler found because `ContentExtractionPipeline` calls it.
- **`AppSettings` boundary:** `normalizeFeedURL`, `refusedFeedScheme` and `feedKey` became statics of a new `FeedURL` enum in the module. `AppSettings` kept forwarding functions, so no caller changed.
- **Xcode:** a static-library target `NewsCore` (Swift 6). It got SwiftSoup through the existing `NewsParsingDependencies` product, and `News`, `NewsTestRunner`, `NewsHarness` and `NewsTests` depended on it and linked it. All five targets set `SWIFT_PACKAGE_NAME = News`.
- **SwiftPM:** a `NewsCore` target depending on `NewsParsingDependencies`, with `News` depending on it.
- **Imports:** 131 app files got `import NewsCore`. The test targets got a single `@_exported import NewsCore` in `Tests/TestDefaults.swift`, which all three compile, instead of edits to the files under `Tests/Native` and `Tests/Harness`.

The 549 missing-type errors involve 50 distinct internal types:

- `MuteRules`: 31;
- `CatalogSet`: 18;
- `EventMatchRow`: 16;
- `FiniteBriefing`: 13;
- `ArticleQueryCursor`: 12;

This was only the first wave. Making those types `package` exposes their members, which are internal, next. The module has about 1,360 member declarations without an access keyword; that is an upper bound, since the count includes locals. 248 declarations were already `public`. Every struct the app builds with a memberwise initializer also needs a hand-written `package init`, because memberwise initializers never cross a module boundary. The estimate is 300 to 600 `package` edits across about 25 files, plus about a dozen initializers.

## Findings for future work

1. **Folder exceptions do not exclude Swift sources.** Xcode ignores folder entries in `membershipExceptions` for Swift sources: with `NewsCore` listed for the four targets and every other folder listed for `NewsCore`, both `News` and `NewsCore` compiled all 136 files. A module needs its own top-level folder with its own synchronized group. That changes the repository layout, and with it `script/format.sh`, `script/changed_atoms.sh`, `.sonarcloud.properties` and `.github/labeler.yml`.
2. **Same-named files are refused.** Xcode will not build a target that sees two files with the same name, here two `StoryImportance.swift` files. A type split must give the new file a different name, or keep the files in targets that never see each other.
3. **`ContentExtractionPipeline` brings `ArticleContentRedactor` along.** Any module holding the extraction pipeline must hold the redactor too (about 200 lines, which import NaturalLanguage).

## Decision

Reject the module for now and revert the spike. The review's kill rule applies on two counts:

- **Access-control churn:** 300 to 600 `package` edits plus hand-written initializers, for a 10,000-line slice.
- **Scope expansion:** a repository re-layout (finding 1) that the spike was not authorised to make.

The expected gain does not justify either. The incremental loop is already at 5 s. The slice is about 17% of `Sources/`, so the test-bundle build could drop by about a tenth at best, while a Release module boundary risks making the cold app build slower.

## Consequences

- The duplicate compile stays for now. It is better removed by shrinking `NewsTestRunner` and `NewsHarness` as native Swift Testing suites take over (#1070, item C of the native-integration plan) than by a module boundary.
- **Revisit when:** after C, if the test-bundle build is still the bottleneck. The move would then be one scripted, mechanical package-access pass over the full core (the projection above), with its own measured before and after, rather than a hand-edited slice.

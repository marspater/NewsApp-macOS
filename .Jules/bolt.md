## 2024-10-24 - Avoid O(N) array scans with URL canonicalizations during SwiftUI view evaluation

**Learning:** In `SavedStoriesManager.swift`, the `isSaved` method was previously implemented as an O(N) scan over the `savedArticles` array. Inside the scan, it performed `article.normalizedLink == $0.normalizedLink`, which parsed the URL via `URLComponents` during every loop iteration. Because `isSaved` is called frequently during `@MainActor` SwiftUI view evaluations (like filtering articles in `ArticleListView` and rendering `ArticleCardView`), this caused thousands of expensive and unnecessary URL canonicalization strings allocations and parsing operations.

**Action:** UI state managers that provide lookup capabilities (like `isSaved` or `isRead`) should maintain internal `Set<String>` collections of identifiers to allow O(1) lookups, especially if the legacy comparison logic involved expensive operations. Future Bolt runs should prefer introducing parallel `Set` tracking for `@Published` arrays if elements are frequently checked for containment during view rendering.

## 2025-01-08 - Use `NSCache` for expensive string computations in UI state managers

**Learning:** `ReadManager.isRead(_:)` was repeatedly invoking `ArticleIdentity.reconcileLegacyId`, which calls `URLComponents` during URL canonicalization. Because `isRead` is heavily queried during `@MainActor` SwiftUI view evaluations (e.g., when rendering `ArticleListView` to filter articles or `ArticleCardView` to show unread badges), this resulted in excessive and redundant URL string allocation and parsing. A standard Swift `Dictionary` could not be used for caching here because it would require mutating `self` in ostensibly read-only methods (`isRead` cannot be `mutating` in a reference type natively used in views without explicit and complex property wrapper/sync coordination, or wrapping in an actor causing async boundary issues).

**Action:** When caching the results of expensive, non-trivial string operations (like URL canonicalization or ID reconciliation) inside SwiftUI `@MainActor` UI state managers, prefer using `NSCache<NSString, NSString>`. `NSCache` provides thread-safe, non-mutating setter access, enabling transparent memoization in read-only methods like `isRead` without causing data races, async propagation overhead, or view evaluation bottlenecks.
